# Pixi.js vs Canvas 2D — 확장 시 비교

포켓몬 디펜스(`js/gameDemo.js`)의 **현재 구현**을 기준으로, 프로젝트 규모가 커졌을 때 **Pixi.js(WebGL)** 와 **Canvas 2D API 단독** 중 어떤 선택이 유리한지 정리한 문서입니다.

관련 구현: [`game-mechanics.md`](game-mechanics.md) · [`readme.md`](../readme.md)

---

## 1. 현재 프로젝트 기준선

### 아키텍처 (하이브리드)

| 영역 | 기술 | 담당 |
|------|------|------|
| 전투 필드 렌더링 | **Pixi.js v7.4.2** | 적·타워 스프라이트, 투사체, 이펙트, 오라, HP바 |
| 말판 배치·이동 입력 | **DOM 그리드 + jQuery** | 10×10 `grid-cell`, 드래그·클릭, `occupied` 상태 |
| HUD·보관함 | **DOM + jQuery** | 뽑기, 강화 패널, 드래그 배치 |

Pixi 캔버스는 `pointer-events: none` — **마우스 입력을 받지 않습니다.**  
타워 이동은 `moveUnit()`에서 `unit.sprite.x/y`만 갱신하고, 실제 클릭·드래그는 DOM이 처리합니다.

### 현재 렌더링 규모 (대략)

| 항목 | 값 | 코드·상수 |
|------|-----|-----------|
| 필드 크기 | 900×900 | `FIELD` |
| 말판 그리드 | 10×10, 칸 54px | `GRID`, `CELL` |
| 필드 적 상한 | 100마리 | `FIELD_LIMIT` |
| 말판 타워 상한 | 100기 | 그리드 전체 |
| Pixi 레이어 | 5개 | `gridLayer` · `unitLayer` · `enemyLayer` · `fxLayer` · `uiLayer` |
| 게임 루프 | `app.ticker` → `onTick` | 적 이동, 공격, 투사체, 이펙트, 오라 |

이 규모에서는 Pixi와 Canvas 2D **모두 60fps 근처로 충분히 동작 가능**합니다.  
차이는 주로 **코드 구조·확장 시 유지보수**에서 드러납니다.

## 2. 규모 확장 가정 (시나리오)

아래는 “이 디펜스 게임이 더 커진다”고 가정한 단계별 시나리오입니다.

| 단계 | 가정 | 예시 |
|------|------|------|
| **S — 현재** | 적 ≤100, 타워 ≤100, 필드 900² | 현재 `gameDemo.js` |
| **M — 중형** | 적 300~500, 타워 200+, 맵 2~4배, 웨이브 동시 3~5겹 | 대형 맵, 다중 경로 |
| **L — 대형** | 적 1,000+, 파티클·탄막 수백, 맵 스크롤/줌 | 장시간 고밀도 전투 |

문서 후반의 추천은 이 단계를 기준으로 합니다.

## 3. Pixi.js — 장단점 (확장 시)

### 장점

#### (1) GPU 배칭 · 동일 텍스처 대량 렌더링

포켓몬 CDN PNG처럼 **같은 텍스처를 수백 번** 그릴 때 WebGL 배칭이 유리합니다.  
적·타워가 늘어날수록 Canvas 2D의 `drawImage` 반복 호출보다 **드로우 호출 절감** 효과가 큽니다.

#### (2) 씬 그래프 (Container · 레이어)

현재 적 하나는 `Container` 안에 스프라이트 + HP바 + 보스 링이 묶여 있고, `container.x/y`만 바꿉니다.

- 확장 시: 상태이상 아이콘, 쉴드, 이름표, 버프 스택 UI를 **자식으로 추가**하기 쉬움
- 맵 스크롤 시: `stage` 또는 상위 `Container`만 이동하면 전체가 따라감

Canvas 2D에서는 매 프레임 **부모 좌표 + 자식 오프셋**을 수동 계산해야 합니다.

#### (3) 이펙트·투사체 수명 관리

`fxLayer`에 `Graphics`·`Sprite`를 올리고 `destroy()`로 제거하는 패턴이 이미 정착되어 있습니다.

- `projectiles[]`, `effects[]`와 Pixi 디스플레이 객체가 1:1로 대응
- 규모가 커져도 **객체 풀링**을 Pixi `ParticleContainer`·커스텀 풀과 결합하기 수월

#### (4) 애니메이션 · 텍스처 파이프라인

- `PIXI.Assets` + `textureCache` — CDN 대량 로드
- `AnimatedSprite` — GIF 공격 연출 (`playAttack`)
- 스프라이트시트·아틀라스로 전환 시 Pixi 생태계가 성숙

Canvas 2D만으로 GIF·아틀라스·비동기 로드를 모두 직접 구현해야 합니다.

#### (5) 마스크 · 필터 · 고해상도

- 버프 오라 말판 클리핑: `auraLayer.mask = fieldMaskGfx`
- `resolution: devicePixelRatio`, `autoDensity` — Retina 대응 내장
- 확장 시: 글로우, 블러, 픽셀화 등 **필터 체인** 추가 가능

#### (6) 게임 루프와 렌더 분리

`onTick`에서 좌표·상태만 갱신하면 Pixi가 렌더합니다.  
대규모 씬에서 **“로직 틱”과 “그리기” 분리**가 코드 가독성에 유리합니다.

### 단점

| 항목 | 설명 |
|------|------|
| **번들 크기** | `pixi.min.js` 추가 (~수백 KB). 교육·임베드 환경에서 부담 |
| **WebGL 의존** | 구형 환경·일부 WebView에서 WebGL 실패 시 폴백 필요 (CanvasRenderer 또는 자체 폴백) |
| **디버깅 곡선** | 씬 그래프·텍스처 메모리·배칭 이슈는 Canvas보다 추상화가 깊음 |
| **오버킬 가능** | 정적 UI·단순 차트만 그릴 때는 Pixi가 과함 |
| **벡터 매 프레임 재그리기** | 슬로우 오라·버프 오라처럼 `Graphics.clear()` 후 매 프레임 path를 다시 그리는 연출은 **Pixi든 Canvas든 CPU 부담이 비슷** — GPU 배칭 이점이 줄어듦 |

## 4. Canvas 2D 단독 — 장단점 (확장 시)

### 장점

#### (1) 의존성 없음 · 단순 배포

`<canvas>` + 네이티브 API만으로 동작. `file://`·CDN 차단 환경에서도 상대적으로 단순합니다.

#### (2) 전체 그리기 흐름이 한곳에 모임

`renderField(ctx)` 한 함수에서 배경 → 적 → 타워 → 이펙트 순으로 그리면 **디버깅 시 “무엇이 화면에 나갔는지” 추적이 직관적**일 수 있습니다.

#### (3) 소규모·중규모에서 성능 충분

스프라이트 수백 장 수준의 `drawImage`는 모던 브라우저에서 여전히 실용적입니다.  
**S~M 단계**에서는 Pixi와 체감 차이가 작을 수 있습니다.

#### (4) 레거시·제한 환경

WebGL을 쓰기 어려운 환경(일부 구형 IE, 특수 키오스크)에서는 Canvas 2D가 **호환성 면에서 유리**할 수 있습니다.  
(현재 프로젝트는 Pixi 7 + WebGL 전제)

#### (5) 입력을 Canvas에 통합할 때

DOM 그리드 없이 **순수 Canvas 단일 캔버스**로 가면 HTML 레이어가 줄어듭니다.  
다만 hit test·드래그·포커스는 **전부 직접 구현**해야 합니다.

### 단점

#### (1) 렌더 루프 보일러플레이트

규모가 커지면 매 프레임:

```text
clearRect → 배경 → (clip) 오라 → 적[N] → 타워[M] → 투사체[P] → 이펙트[E] → UI 오버레이
```

- **그리기 순서**를 코드로 직접 유지
- 카메라 스크롤·줌 시 모든 좌표 변환을 수동 적용
- 레이어 개념이 없어 **실수로 순서가 꼬이기 쉬움**

#### (2) 객체 묶음 관리

적 + HP바 + 보스 링 + 디버프 아이콘을 “한 덩어리”로 움직이려면  
`{ x, y, children: [...] }` 형태의 **자체 씬 트리**를 만들어야 합니다.  
Pixi `Container`가 해주는 일을 직접 재구현하는 셈입니다.

#### (3) 이펙트 폭증 시 코드 비대화

현재 Pixi 기준 연출 예:

- `fireLaserBeam`, `fireGalagaShot`, `fireBurstShot`, `spawnAoeSplashRing`
- `drawEnemySlowAura`, `drawBuffUnitAura`, `drawLegendaryUnitAura`

Canvas 전환 시 각각 **spawn 데이터 구조 + render 분기** 쌍으로 관리해야 합니다.  
**L 이상**에서 이펙트 종류가 늘면 유지보수 비용이 Pixi보다 빠르게 증가합니다.

#### (4) GIF · 스프라이트시트 · DPR

| 기능 | Canvas 2D |
|------|-----------|
| GIF 공격 | 프레임 파싱 또는 사전 변환 필수 |
| 텍스처 캐시 | `Image` + Promise 래퍼 직접 작성 |
| Retina | `canvas.width/height` × `devicePixelRatio` 수동 |
| 말판 밖 클리핑 | `ctx.clip()` 매 그룹마다 save/restore |

#### (5) 성능 한계가 오는 지점

대략 아래가 겹치면 Canvas 2D가 먼저 병목에 걸리기 쉽습니다.

- 동시 `drawImage` **1,000회 이상**/프레임
- 매 프레임 전체 `clearRect` + 전 레이어 풀 리드로우
- 이펙트·탄막 **수백~수천** 개 (벡터 path 반복)
- 모바일 저사양 + **장시간** 고밀도 전투

이때는 Pixi(WebGL) 또는 **오프스크린 캐시·타일 레이어·객체 풀** 등 추가 최적화가 필요하며, 결국 Pixi가 내장한 것과 비슷한 인프라를 직접 짜게 됩니다.

## 5. 입력(타워 이동) — 규모와 무관한 공통점

타워 드래그·클릭·보관함 배치는 **현재 DOM 그리드**가 담당합니다.

| 방식 | Pixi 프로젝트 | Canvas 프로젝트 |
|------|---------------|-----------------|
| 말판 입력 | DOM `grid-overlay` (권장, 현재 방식) | **동일하게 가져갈 수 있음** |
| 대안 | Pixi `interactive` + hitArea | Canvas 좌표 hit test 직접 구현 |

**규모가 커져도** “10×10 배치 UI”는 DOM이 CSS 상태(`occupied`, `evo-ready`, `drag-target`)와 궁합이 좋습니다.

확장 시나리오:

| 변화 | 입력 측 영향 |
|------|----------------|
| 맵만 커짐 (20×20, 30×30) | DOM 셀 수 증가 — 여전히 실용적 |
| 맵이 거대 + 스크롤 | DOM 그리드도 스크롤 동기화 필요 — Pixi/Canvas **둘 다** 카메라 연동 코드 필요 |
| 자유 배치 (그리드 없음) | DOM 그리드 부적합 — Pixi hitArea 또는 Canvas 거리 기반 hit test |

→ **렌더러 선택과 별개로**, 배치 UX 설계가 먼저입니다.

| 항목 | Pixi.js | Canvas 2D |
|------|---------|------------|

| **벡터 이펙트 대량** | ○ (CPU 비슷) | ○ (CPU 비슷) |

| **GIF/시트 애니** | ◎ | ×~△ |
| **텍스처 로더** | ◎ Assets | △ 직접 |
| **마스크/필터/DPR** | ◎ | △ 직접 |

## 8. 이 프로젝트에서의 실전 권장 로드맵

현재 하이브리드(**Pixi 전투 + DOM 배치 + DOM HUD**)를 유지한 채 규모를 키울 때의 우선순위입니다.

### 유지해도 좋은 것

1. **DOM 그리드** — 말판 배치·드래그·합성 하이라이트 (`grid-overlay`)
2. **Pixi 레이어 분리** — 배경 / 유닛 / 적 / FX / UI
3. **`textureCache` + CDN** — 종 id 기반 텍스처 재사용
4. **`units[]` / `enemies[]` + 디스플레이 객체** — 로직과 뷰 분리

### 규모 확장 시 Pixi 쪽에서 손볼 것

| 우선순위 | 내용 |
|----------|------|
| 1 | 이펙트·투사체 **객체 풀링** (`projectiles`, `effects` 생성·destroy 감소) |
| 2 | 정적 맵·관중석 **RenderTexture 캐시** (매 프레임 재그리기 제거) |
| 3 | 적 대량 시 **스프라이트 아틀라스** (드로우 배칭 극대화) |
| 4 | 오라 등 `Graphics.clear()` 연출 → **스프라이트 시퀀스 또는 셰이더**로 전환 검토 |
| 5 | 화면 밖 유닛 **culling** (`container.visible = false`) |
| 6 | 맵 스크롤 시 `stage` pivot + DOM 그리드 `transform` 동기화 |

### Canvas 2D로 전면 전환을 검토할 만한 경우

- Pixi 번들을 **반드시** 제거해야 하는 임베드 환경
- 전투 연출을 대폭 줄이고 **정적·저애니** 위주로 단순화
- 팀이 WebGL/Pixi 없이 Canvas 2D만 다루는 경우 (단, L 규모 목표면 재검토 필요)

## 9. 요약

| 질문 | 답 |
|------|-----|
| 타워 이동은 Pixi/Canvas 차이가 있나? | **거의 없음** — DOM 그리드가 입력을 담당 |
| 현재 규모에서 성능 차이? | **체감 작음** — 둘 다 충분 |
| 규모가 커지면? | **Pixi(WebGL) 쪽이 성능·구조 모두 유리**해지는 구간이 빠름 |
| 코드량은? | 소규모는 Canvas가 단순해 보일 수 있으나, **이펙트·애니·레이어가 늘수록 Pixi가 유리** |
| 이 프로젝트 추천 | **Pixi + DOM 하이브리드 유지**, L 이상 목표 시 풀링·아틀라스·캐시 레이어 추가 |

**한 줄:** 배치 UI는 DOM으로, “많이 움직이고 많이 그리는 전투”는 Pixi로 — 규모가 커질수록 이 분업이 더 분명해집니다.
